# Hash

DanKG needs a content hash for two things: keying the per-file index cache
(`graph/cache.rs`) and stamping the config into that cache, so that an edited
`.dankg/config` invalidates every entry rather than leaving a stale one
behind. Neither use is security-bearing -- a collision costs a stale parse,
which the next edit corrects -- so this is FNV-1a: eight lines, no tables,
no dependency, exactly the standard-library-only constraint decision 1
holds everywhere else.

This file is the literate source; `hash.rs` itself is generated by
`dankg tangle` and is never committed. See the pilot notes at the bottom of
this file for how to reproduce that.

## Crate scaffold

One block below uses `path=` to land outside the heading-derived tree
entirely (architecture.org, *Tangle > Placement*): the `Cargo.toml`. It is
fenced `rust` even though the manifest isn't Rust source -- tangle selects
blocks by fence language matching `--lang`, never by file extension, so a
`toml`-language block would simply be invisible to a `--lang rust` run.
`comment_prefix` in `tangle.rs` already keys the generated banner off the
*destination* extension for exactly this reason.

There is no separate `lib.rs`: Cargo's `[lib] path` key can point straight
at wherever the heading-derived placement puts the real module, so `hash.rs`
below -- placed by containment, exactly the way a corpus-wide tangle would
place it -- *is* the crate root. Nothing here overrides tangle's own
placement for it; the manifest just points at where that placement already
lands.

```rust name=cargo_manifest path=Cargo.toml
[package]
name = "dankg-hash-pilot"
version = "0.1.0"
edition = "2024"

[lib]
name = "dankg_hash_pilot"
path = "hash.rs"

[dependencies]
```

## The hash

Rust's inner-doc-comment (`//!`) has to be the first thing in the file it
documents, so it gets its own small leading block rather than living inside
`fnv1a`'s. Everything past this paragraph is content that lands in
`hash.rs`, in document order, folded together under this section's own
heading regardless of how deep a block's immediate subheading sits
(architecture.org, *Tangle > Placement*: containment decides the file,
never `deps=`).

This is also the file's one deliberately duplicated sentence, not a habit
to repeat: `//!` is what a `cargo doc` reader sees with no markdown in
front of them, so it needs *something*, but it stays a pointer rather than
a second copy of the paragraph above -- the convention this pilot settled
on (see *Pilot notes*) is that the surrounding prose is the canonical
explanation, and a doc comment inside a tangled block earns its keep only
by saying something the prose doesn't, or by pointing back to it.

```rust name=module_doc
//! A 64-bit content hash (FNV-1a). See `literate/hash.md#hash` for why.
```

The mix step is the entire algorithm: XOR a byte into the state, then
multiply by the FNV prime, for every byte in the input. `OFFSET` and
`PRIME` are FNV-1a's published constants, not tunable.

```rust name=fnv1a
pub fn fnv1a(bytes: &[u8]) -> u64 {
    const OFFSET: u64 = 0xcbf2_9ce4_8422_2325;
    const PRIME: u64 = 0x0000_0100_0000_01b3;

    let mut h = OFFSET;
    for byte in bytes {
        h ^= *byte as u64;
        h = h.wrapping_mul(PRIME);
    }
    h
}
```

Cache file names all need the same shape, so the hex form is fixed-width
rather than however many digits the value happens to need.

```rust name=hex
pub fn hex(value: u64) -> String {
    format!("{value:016x}")
}
```

The inverse, used to compare a stored hash against a freshly computed one
without keeping either side's numeric form around longer than it has to be.

```rust name=parse_hex
pub fn parse_hex(text: &str) -> Option<u64> {
    u64::from_str_radix(text, 16).ok()
}
```

## Tests

Three cases: published FNV-1a reference vectors (so a transcription mistake
in the constants above cannot pass silently), the hex round-trip at its
fixed width, and a sanity check that a one-byte change actually changes the
hash.

```rust name=tests
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn matches_the_reference_vectors() {
        assert_eq!(fnv1a(b""), 0xcbf2_9ce4_8422_2325);
        assert_eq!(fnv1a(b"a"), 0xaf63_dc4c_8601_ec8c);
        assert_eq!(fnv1a(b"foobar"), 0x85944171f73967e8);
    }

    #[test]
    fn hex_round_trips_at_fixed_width() {
        let h = fnv1a(b"notes/ideas.md");
        assert_eq!(hex(h).len(), 16);
        assert_eq!(parse_hex(&hex(h)), Some(h));
    }

    #[test]
    fn differs_on_a_one_byte_change() {
        assert_ne!(fnv1a(b"# One\n"), fnv1a(b"# Two\n"));
    }
}
```

## Pilot notes

This is the bootstrap pilot for the question "can dankg build itself,
dankg-style" (see architecture.org's Tangle section and the advisory this
file grew out of). `literate/.dankg/config` scopes `literate/` as its own
root with:

```
[tangle.rust]
ext     = rs
command = cargo test --manifest-path {dir}/Cargo.toml
```

Reproduce with the repo's own `dankg` binary:

```
cargo run --bin dankg -- tangle literate/hash.md --lang rust
```

That assembles `Cargo.toml` and `hash.rs` into `literate/.dankg/build/rust/`
and then runs `cargo test` against the result -- no `glue` step is
configured because a single flat module has no subdirectory tree needing
`mod` declarations; that only becomes necessary once this scales past one
file (decision 27).

### Two frictions found, and how they were closed

- **No blank line between concatenated blocks.** `tangle.rs`'s
  `render_file` used to butt one block's `source` directly against the
  next, so two functions with a blank paragraph of prose between them in
  this file still landed touching in `hash.rs`, harmless to `rustc` but
  unreadable next to a diff of the hand-written original. Fixed upstream,
  not worked around here: `render_file` now joins consecutive blocks with
  one blank line, the same "exactly one blank line, every time" shape
  `result.rs`'s write-back already commits to (`src/tangle.rs`,
  `consecutive_blocks_in_one_file_get_a_blank_line_between_them`).
- **Doc comments duplicating or dropping the surrounding prose.** No code
  fix at the *tangle* level -- teaching it to synthesize a `//!`/`///` from
  nearby markdown would mean reading what a block's prose *means* well
  enough to summarize it, exactly the line decision 1 and decision 27
  already refuse to cross. The convention: the markdown prose is the one
  canonical explanation, and a doc comment inside a tangled block is
  either a short pointer back to it (as `module_doc` now is) or says
  something the prose genuinely doesn't. But conventions get forgotten,
  and this one wasn't self-enforcing: see below.

### Enforcing the convention: `glue/rust-doclint.py`

A convention nobody checks drifts. `[tangle.rust] glue` (`literate/.dankg/config`)
now also runs `glue/rust-doclint.py` -- an opt-in, external script (never
DanKG's own code, decision 27) that reads a tangled block's own doc comment
straight out of the source `.md` and flags one that borrows a clause from
the surrounding prose, on stderr, never failing the build.

The manifest that makes this possible grew a second version to support it:
`.dankg-tangle-manifest.json` now carries each file's contributing blocks,
in document order, with the `line`/`end_line` of each one's fence in the
*source* -- the same fields `result.rs` already tracks for write-back,
just exposed (`src/tangle.rs`'s `ManifestEntry`/`BlockEntry`). That is
what lets the script window its prose comparison to *just* the paragraph
immediately before a block, instead of the whole file -- proven with a
fixture where two blocks share the exact same borrowed clause but only one
of them sits next to the paragraph it came from: only that one gets
flagged (`glue/rust-doclint.py`'s own module doc explains the windowing;
the fixture lives in this pilot's own history, not the repo, since it was
a throwaway proof rather than a fixed test corpus).

The first version compared whole comments against whole paragraphs and
missed the real case in this very file: the module-doc rewrite kept one
clause -- *"a collision costs a stale parse, which the next edit
corrects"* -- word for word inside an otherwise fully reworded sentence.
Whole-string containment can't see a partially-reused sentence; the script
now splits both sides into clauses (on `.`/`!`/`?`/`--`) and checks
containment clause by clause, which is what actually caught it.
